# Simplifications

Where the simulation differs from real Kafka. Add an entry for every simplification (real behaviour vs ours, and why).

| Area | Real Kafka | Kafka Playground | Why |
|---|---|---|---|
| Partition placement | In KRaft the controller's `StripedReplicaPlacer` stripes replicas across brokers and racks from a randomised start | Round-robin over brokers sorted by id, from a seeded random start; racks ignored | Same spreading idea, predictable for lessons; racks arrive with multi-AZ (v0.5) |
| Replication (M1 only) | Each partition has `replication.factor` replicas; HW = min LEO over the ISR | One replica per partition; topics with RF > 1 are rejected; HW = LEO after every append | Replication, ISR and elections arrive in M4 |
| Broker removal (M1 only) | Partitions can be reassigned to other brokers before a broker is decommissioned | Removing a broker that leads partitions is rejected | Reassignment arrives with multi-broker work (M4) |
| Sticky partitioner (null key) | Uniform sticky partitioner (KIP-480, KIP-794): switch after `batch.size` bytes, or up to 2 × `batch.size` while batches are not full; with adaptive partitioning the next partition is weighted by broker queue sizes | Switch as soon as `batch.size` bytes were produced to the partition; next partition uniform over all partitions (may repeat), from the seeded RNG | No batching or broker queues are modelled in M1; the "stay, then move" pattern is what matters for lessons |
| Key serialisation | `StringSerializer` encodes with a configurable charset, UTF-8 by default | Always UTF-8; an unpaired surrogate becomes `?` (0x3f), as Java's encoder does | Non-default key encodings are not used in lessons |
| Network | Variable latency; requests queue in sockets and on brokers | Fixed one-way client↔broker delay (`networkDelayMs`, default 1 ms); no queueing | Enough to show cause → effect in the event log; resource model is v0.2 |
| Producer batching | Records are grouped into batches per partition (`batch.size`, `linger.ms`) and sent together | Each record is its own request | Batching affects throughput, not the ordering or acks semantics taught in M1 |
| Produce errors and retries | Retriable errors (e.g. `UNKNOWN_TOPIC_OR_PARTITION`) are retried until `delivery.timeout.ms` (120 s) | The first error is reported as `ProduceFailed`; no retries | Retries and idempotence arrive with v0.4 patterns |
| Producer workload | An application decides which topic each record goes to | A simulated producer sends one record per tick to every topic it is connected to, with value `"<producerId>-<n>"` | Game setting: lets one producer feed several topics on the canvas |
| acks=all (M1 only) | Leader waits for every in-sync replica | Same as acks=1, because each partition has one replica | Replication arrives in M4 |
| Consumer fetching | The classic consumer sends FetchRequests from inside `poll()`, one per broker, and long-polls: the broker holds a request until `fetch.min.bytes` are available or `fetch.max.wait.ms` passes. Responses go into a fetch buffer that `poll()` drains; before returning records it sends the next fetch (pipelining). Responses are capped by `fetch.max.bytes` (50 MiB) and `max.partition.fetch.bytes` (1 MiB); fetch sessions (KIP-227) make requests incremental; positions are looked up with OffsetFetch / ListOffsets requests | Modelled: long poll with `fetch.min.bytes` / `fetch.max.wait.ms`, one request per leader, fetch buffer, pipelining, two network trips, `RecordConsumed` when `poll()` returns the record. Not modelled: the byte caps (a response carries every available record), fetch sessions, and the offset lookups (a new position is known at once). Record size is the producer's `messageSizeBytes` game setting, without batch overhead | The byte caps only matter for very large backlogs; the lookups are a few ms at startup |
| Records per poll | `max.poll.records` caps one `poll()`; records come from the completed fetches in arrival order, leftovers stay buffered; partition order in requests follows the client's fetch session | Same cap and buffer behaviour; the partition order in each fetch request rotates by one, so with a small `max.poll.records` no partition is always drained last | Deterministic and starvation-free |
| Auto-commit timing | Classic consumer: checked inside `poll()`, and a blocked `poll()` wakes up for it (`timeToNextPoll`); the newer KIP-848 consumer runs a background timer | Checked at the start of each `poll()` and when the auto-commit deadline passes while the application is blocked in `poll()`: positions returned by earlier polls are committed | Classic protocol first (architecture §4.3); to be confirmed by the fidelity harness (M5) |
| Consumer groups (M1 only) | Many consumers share a group and split its partitions | One consumer per group; it reads every partition of the topics it is connected to | Group coordinator and rebalancing arrive in M3 |
| Manual commits (M1 only) | `commitSync` / `commitAsync` from application code | With `enable.auto.commit = false` nothing is committed | Manual commit commands arrive in M3 |
| Consumer crash | A crashed consumer is detected by the group coordinator after `session.timeout.ms` | `KillConsumer` stops it instantly without committing; `RestartConsumer` resumes from the committed offsets | Session timeouts arrive with groups (M3) |
| Retention (M1 only) | Old log segments are deleted by `retention.ms` / `retention.bytes`, moving the log start offset up | Logs never shrink; `logStartOffset` stays 0 | Retention and compaction arrive in v0.4 |
| Topic deletion | Deletion is asynchronous; the group's committed offsets for the topic are cleaned up later | The topic disappears at once; in-flight produce requests fail; committed offsets stay in the group | Keeps the event log easy to follow |
| Time | Wall-clock milliseconds with real jitter | Integer sim milliseconds; ties are broken by scheduling order (`seq`) | Determinism (NFR-4.1) |
| Config changes at run time | Client configs are fixed when a `KafkaProducer` / `KafkaConsumer` is created; changing one means closing the client and creating a new one. Topic partition counts change through `CreatePartitions`; `broker.rack` needs a broker restart | `UpdateConfig` changes a producer or consumer in place: producer changes apply to the next record (a rate change restarts the send schedule), consumer changes from the next `poll()`. In-flight produce requests keep their `acks`; a fetch parked at the broker keeps its `fetch.min.bytes` / `fetch.max.wait.ms`. Topic partitions can only grow; `group.id`, `auto.offset.reset`, the replication factor and `broker.rack` cannot be changed (M3/M4) | Lets the player tune a running flow from the properties panel without rebuilding it |
| Client metadata refresh | Clients refresh cluster metadata every `metadata.max.age.ms` (5 min) or after a metadata error, after a MetadataRequest round trip. A subscribed consumer that sees new partitions rebalances its group | Modelled with the real default: producers and consumers use their cached partition counts until the next refresh, which is applied instantly at the next send / `poll()` once the age has passed (or after `UNKNOWN_TOPIC_OR_PARTITION`). A consumer adds the new partitions to its assignment without a rebalance (groups are M3), starting them with `auto.offset.reset` | Shows the real "new partitions get no traffic for up to 5 minutes" and "`latest` skips records on new partitions" effects |
| New partition placement | `CreatePartitions` places new replicas with the controller's replica placer | New partitions continue the topic's round-robin stripe over the brokers sorted by id, starting from partition 0's leader (with one broker, all on it) | Deterministic; placement detail arrives with multi-broker work (M4) |
