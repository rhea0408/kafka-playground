# Simplifications

Where the simulation differs from real Kafka. Add an entry for every simplification (real behaviour vs ours, and why).

| Area | Real Kafka | Kafka Playground | Why |
|---|---|---|---|
| Partition placement | In KRaft the controller's `StripedReplicaPlacer` stripes replicas across brokers and racks from a randomised start (unseeded `java.util.Random`) | The rack-unaware path of `StripedReplicaPlacer` is ported (sorted brokers, random start offset, consecutive brokers per partition, one step further per partition, reshuffle after one round), with the engine's seeded RNG; racks are ignored (M4-T2) | Same spread of replicas and preferred leaders; deterministic. Racks arrive with multi-AZ (v0.5) |
| KRaft controller | A quorum of controllers (3 or 5 nodes) elects an active controller via Raft; it can fail over; brokers replay the metadata log; in combined mode a node is both broker and controller | One abstract controller, always up, not a broker (ADR 0005). Changes reach brokers at once; heartbeats, registration, AlterPartition and controlled shutdown cost one network delay each way | Controller failover is a later milestone; the lessons are about brokers |
| Broker fencing | The controller scans for stale brokers every `broker.session.timeout.ms / 8` | Fenced exactly `broker.session.timeout.ms` (9 s) after the last heartbeat arrived; heartbeats exactly every 2 s | Within about a second of Kafka; deterministic |
| Broker crash | A JVM crash on a live host: the OS still sends buffered data; a machine crash loses it | `KillBroker` is a process crash: messages already on the wire arrive, nothing new is sent; its in-memory purgatories vanish. Disks are never lost | acks=1 loss then needs follower lag, as in Kafka |
| Unclean election timing | With `unclean.leader.election.enable` turned on later, the controller's periodic task (`unclean.leader.election.interval.ms`, 5 min) or the next broker event elects a leader | Turning it on elects leaders for that topic's offline partitions at once | A 5-minute wait would look like nothing happens |
| Eligible Leader Replicas | KIP-966 is on by default in 4.4 and can be turned off with `eligible.leader.replicas.version=0`; leaders elected as "last known leader" or unclean are RECOVERING until the next ISR change | Always on; the RECOVERING state is not modelled (the election is reported as `unclean`) | Matches a fresh 4.4 cluster |
| Replication | Followers run replica fetcher threads: one per (follower, leader) pair, fetching up to `replica.fetch.max.bytes` from their LEO, long-polling with `replica.fetch.wait.max.ms`; the leader tracks each follower's LEO and last-caught-up time, and HW = min LEO over the maximal ISR (plus caught-up replicas joining it), frozen while ISR < `min.insync.replicas` | Modelled (M4-T3): one fetcher per pair with one request in flight, long poll with `replica.fetch.wait.max.ms`, `replica.fetch.min.bytes` 1, the K3 last-caught-up rule and the K5 HW rule, strict min ISR. Not modelled: byte limits (a response carries everything up to the LEO), fetch sessions, follower throttling | Replication takes about two network delays, as in Kafka |
| Broker removal (until M4) | Partitions can be reassigned to other brokers before a broker is decommissioned | Removing a broker that leads partitions is rejected | Reassignment arrives with multi-broker work (M4) |
| Sticky partitioner (null key) | Uniform sticky partitioner (KIP-480, KIP-794): switch after `batch.size` bytes, or up to 2 × `batch.size` while batches are not full; with adaptive partitioning the next partition is weighted by broker queue sizes | Switch as soon as `batch.size` bytes were produced to the partition; next partition uniform over all partitions (may repeat), from the seeded RNG | No batching or broker queues are modelled in M1; the "stay, then move" pattern is what matters for lessons |
| Key serialisation | `StringSerializer` encodes with a configurable charset, UTF-8 by default | Always UTF-8; an unpaired surrogate becomes `?` (0x3f), as Java's encoder does | Non-default key encodings are not used in lessons |
| Network | Variable latency; requests queue in sockets and on brokers | Fixed one-way client↔broker delay (`networkDelayMs`, default 1 ms); no queueing | Enough to show cause → effect in the event log; resource model is v0.2 |
| Producer batching | Records are grouped into batches per partition (`batch.size`, `linger.ms`, default 5 ms in 4.x) and sent together | Each record is its own request; a queue per partition holds records waiting for a leader or a retry | Batching affects throughput, not the ordering, acks or retry semantics taught here |
| Produce errors and retries | The sender retries retriable errors with exponential backoff until `delivery.timeout.ms` (120 s), up to 5 in-flight requests per connection; the idempotent producer's epoch is producer-wide | Modelled (M4-T7): retries with KIP-580 backoff and KIP-951 skip, `request.timeout.ms` per attempt, `delivery.timeout.ms` (30 s game-tuned), metadata refresh on the right errors, idempotence with PID/epoch/sequence and 5-batch dedup. Limits: 5 in flight **per partition** (one record per request), the epoch bump is per partition, `linger.ms` (4.x default 5) is not modelled | Shows failover without failures and duplicates (acks=all) or with duplicates (acks=1), as in Kafka |
| Producer workload | An application decides which topic each record goes to | A simulated producer sends one record per tick to every topic it is connected to, with value `"<producerId>-<n>"` | Game setting: lets one producer feed several topics on the canvas |
| Manual produce (M2) | `ProducerRecord` can name an explicit partition and carry headers and a timestamp | `ProduceManual` has only a key and a value: the record goes through the partitioner (murmur2 for a key, sticky for a null key) to every topic the producer is connected to | Enough to show key → partition; an explicit partition is a small engine change for a later milestone |
| acks=all | The leader refuses the write with `NOT_ENOUGH_REPLICAS` while ISR < min(`min.insync.replicas`, RF), else parks it (DelayedProduce) until the HW passes it or `request.timeout.ms`; `NOT_ENOUGH_REPLICAS_AFTER_APPEND` in a narrow race | Same rules (M4-T3, K6); the parked request is completed synchronously when the HW moves, so the AFTER_APPEND race practically never happens | Faithful outcome; the race needs concurrent threads |
| Consumer fetching | The classic consumer sends FetchRequests from inside `poll()`, one per broker, and long-polls: the broker holds a request until `fetch.min.bytes` are available or `fetch.max.wait.ms` passes. Responses go into a fetch buffer that `poll()` drains; before returning records it sends the next fetch (pipelining). Responses are capped by `fetch.max.bytes` (50 MiB) and `max.partition.fetch.bytes` (1 MiB); fetch sessions (KIP-227) make requests incremental; positions are looked up with OffsetFetch / ListOffsets requests | Modelled: long poll with `fetch.min.bytes` / `fetch.max.wait.ms`, one request per leader, fetch buffer, pipelining, two network trips, `RecordConsumed` when `poll()` returns the record. Not modelled: the byte caps (a response carries every available record), fetch sessions, and the offset lookups (a new position is known at once). Record size is the producer's `messageSizeBytes` game setting, without batch overhead | The byte caps only matter for very large backlogs; the lookups are a few ms at startup |
| Records per poll | `max.poll.records` caps one `poll()`; records come from the completed fetches in arrival order, leftovers stay buffered; partition order in requests follows the client's fetch session | Same cap and buffer behaviour; the partition order in each fetch request rotates by one, so with a small `max.poll.records` no partition is always drained last | Deterministic and starvation-free |
| Auto-commit timing | Classic consumer: checked inside `poll()`, and a blocked `poll()` wakes up for it (`timeToNextPoll`); the newer KIP-848 consumer runs a background timer | Checked at the start of each `poll()` and when the auto-commit deadline passes while the application is blocked in `poll()`: positions returned by earlier polls are committed | Classic protocol first (architecture §4.3); to be confirmed by the fidelity harness (M5) |
| Consumer groups | Classic protocol (`group.protocol=classic`) or the KIP-848 consumer protocol (`group.protocol=consumer`, broker-side assignment, no global barrier) | Classic protocol only (ADR 0004): JoinGroup / SyncGroup / Heartbeat / LeaveGroup with generations, the client leader assigning, eager and cooperative rebalancing. KIP-848 is a later milestone | The classic protocol is still the 4.x default and shows the barrier, stop-the-world and zombie lessons |
| Static membership and rack-aware assignment | `group.instance.id` lets a restarted member keep its partitions without a rebalance (KIP-345); `client.rack` makes range and the sticky assignors prefer replicas in the same rack (KIP-881) | Not modelled: every restart joins as a new member; assignors ignore racks | Out of scope for M3 (milestone doc); the disabled `group.instance.id` field says so |
| Heartbeat thread timing | The heartbeat thread wakes about every `retry.backoff.ms` (100 ms) to check the poll timer and whether a heartbeat is due | Heartbeats go out exactly every `heartbeat.interval.ms`, and the poll timeout is noticed exactly when it expires | Within 100 ms of Kafka; deterministic |

| Application commits | The application calls `commitSync()` / `commitAsync()` wherever its code says, often in a `ConsumerRebalanceListener` too | A game setting, `commitMode`, stands in for the code: `auto` (only `enable.auto.commit`), commitSync after processing, commitAsync after processing, or commitSync before processing. A failed commit is reported (`CommitFailed`) and the loop goes on. No commits in rebalance callbacks | Covers at-least-once and at-most-once with one setting; the code panel (M7) generates the matching loop |
| Duplicate and skip detection | Kafka has no such thing: duplicates and losses are only visible in the application's results | `DuplicateProcessed` / `RecordsSkipped` compare each record handed to the application with the highest offset its group has handed out for that partition; a crash takes back the records of the batch that were not processed yet. A teaching aid, not Kafka behaviour | Makes FR-2.8 visible |
| Graceful stop | A shutdown hook calls `wakeup()`; the loop finishes, then `close()` commits (auto-commit) and leaves | `StopConsumer` lets the current batch finish, then closes. `RemoveComponent` and a `group.id` change close at once and count the batch as processed | Same outcome as a well-written shutdown hook |
| Consumer crash | A crashed consumer stops heartbeating; the group coordinator removes it after `session.timeout.ms` and rebalances. A restarted process joins as a new member | Same. `KillConsumer` stops the process at once: no commit, no LeaveGroup, no heartbeats; the coordinator notices after the (game-tuned 10 s) session timeout. `RestartConsumer` joins as a new member and resumes from the committed offsets | The instant crash stands in for a process that dies between two instructions |
| Sticky assignor with different subscriptions | When members subscribe to different topics, `AbstractStickyAssignor#generalAssign` runs a balancing search that also prefers keeping partitions with their previous owners | Owned partitions are kept, each free partition goes to the eligible member with the fewest, then partitions move from a member to an eligible one with at least two fewer until nothing can move. With equal subscriptions the real `constrainedAssign` steps are followed | The full search is long and rarely matters for lessons; balance and stickiness still hold (property tests) |
| Group coordinator lookup | FindCoordinator goes to the least-loaded broker; `__consumer_offsets` (50 partitions, `offsets.topic.replication.factor` 3) is created on the first lookup and can't be created with fewer registered brokers | FindCoordinator is a round trip to the first live broker (M4-T8). The internal topic's replication factor is min(3, registered brokers) when it is created (game-tuned, M4 Q9) | Single-broker scenes still get a coordinator |
| JoinGroup member ids | JoinGroup v4+: a new member's first JoinGroup is answered `MEMBER_ID_REQUIRED` with its member id (`<client.id>-<UUID>`), and the client sends JoinGroup again with it | The first JoinGroup is accepted directly; the member id is `<consumer id>-<8 hex digits>` from the seeded RNG | Saves one round trip (2 ms) per join; ids stay deterministic |
| Protocol vote ties and leader re-election | A tie in the assignor vote and the choice of a new leader follow HashMap iteration order | The tie goes to the longest-standing member's preference; the longest-standing (rejoined) member becomes leader | Deterministic |
| New members' join timeout | A new member waiting in its first join phase expires after a fixed 5 minutes | Members waiting in JoinGroup or SyncGroup never expire | No join phase here lasts that long |
| onJoinPrepare commit errors | `onJoinPrepare` keeps waiting (until `joinPrepareTimer`, the rebalance timeout) when the auto-commit fails with a retriable error such as `COORDINATOR_NOT_AVAILABLE`, and goes on after success or a non-retriable error | Any answer ends the wait, success or error; the timeout (D1 in M4-decisions) is modelled | A retried commit during the join prepare is rare; the next auto-commit covers it |
| Committed offsets storage | The coordinator writes commits and group metadata to `__consumer_offsets` (compacted) and answers commits once replicated; SyncGroup also waits for the group record; a new leader loads the groups (`COORDINATOR_LOAD_IN_PROGRESS` meanwhile) | Commits and group metadata are records in a real replicated `__consumer_offsets`; commits are answered at the HW (M4-T8). Not modelled: compaction, SyncGroup waiting for its record, the loading time (instant), tombstones on topic deletion (offsets of deleted topics are skipped when loading) | Coordinator failover and lost unreplicated commits behave as in Kafka |
| Session timeout limits | The broker checks `session.timeout.ms` against `group.min.session.timeout.ms` (6 s) / `group.max.session.timeout.ms` (30 min) when JoinGroup arrives and answers `INVALID_SESSION_TIMEOUT` | The schema checks the same limits (the broker defaults) when the field is set, with the same error name | The limits are not configurable yet; the player sees the error in the panel at once |
| Poll and rebalance timeouts | `max.poll.interval.ms` (300 s) is also the rebalance timeout; `session.timeout.ms` is 45 s | Game-tuned defaults 30 s and 10 s, labelled `game-tuned` with the real defaults beside them (CLAUDE.md rule 6) | Lessons would take minutes otherwise |
| Retention (until v0.4) | Old log segments are deleted by `retention.ms` / `retention.bytes`, moving the log start offset up | Logs never shrink; `logStartOffset` stays 0 | Retention and compaction arrive in v0.4 |
| Topic deletion | Deletion is asynchronous: the controller records it and brokers delete the logs in the background. When a broker applies the deletion, the group coordinator deletes every group's committed offsets for the topic (`GroupCoordinator#onPartitionsDeleted`) | The topic disappears at once; in-flight produce requests fail; parked fetches answer `UNKNOWN_TOPIC_OR_PARTITION`; committed offsets for the topic are deleted at once (no event) | Keeps the event log easy to follow |
| Commits after a topic is re-created | The classic consumer tracks positions and commits by topic name (OffsetCommit gained topic IDs only in v10, for the KIP-848 consumer). Fetch v13+ names topics by topic ID (KIP-516), and a broker answers `UNKNOWN_TOPIC_ID` when the ID no longer matches. A commit for a topic that does not exist fails with `UNKNOWN_TOPIC_OR_PARTITION`. What the client does with a position after `UNKNOWN_TOPIC_ID` is our best reading; the fidelity harness (M5) should check it | Each consumer position remembers the topic ID it belongs to, set when the position starts or resets. Fetch requests carry it; on `UNKNOWN_TOPIC_ID` the consumer drops the position and starts the partition again from the committed offset (deleted with the old topic) or `auto.offset.reset`, so it never reads the new topic from an offset of the old one (M3-T0, F-b). Records already in the fetch buffer from the old topic can still be returned once. A commit for a deleted topic, or of a position from an earlier life of a re-created topic, is dropped (nothing stored, no `OffsetCommitted`) | A committed offset never points past the end of the topic it belongs to, and a position never skips the start of a re-created topic, so lag and restarts stay meaningful |
| Time | Wall-clock milliseconds with real jitter | Integer sim milliseconds; ties are broken by scheduling order (`seq`) | Determinism (NFR-4.1) |
| Config changes at run time | Client configs are fixed when a `KafkaProducer` / `KafkaConsumer` is created; changing one means closing the client and creating a new one. Topic partition counts change through `CreatePartitions`; `broker.rack` and `group.initial.rebalance.delay.ms` need a broker restart | `UpdateConfig` changes a producer or consumer in place: producer changes apply to the next record (a rate change restarts the send schedule), consumer changes from the next `poll()` (the assignor list, `session.timeout.ms` and `max.poll.interval.ms` from the next JoinGroup). A `group.id` change closes the consumer and starts it again in the new group, like recreating the client. In-flight produce requests keep their `acks`; a fetch parked at the broker keeps its `fetch.min.bytes` / `fetch.max.wait.ms`. Topic partitions can only grow; the replication factor and the broker configs cannot be changed (M4) | Lets the player tune a running flow from the properties panel without rebuilding it |
| Client metadata refresh | Clients refresh cluster metadata every `metadata.max.age.ms` (5 min) or after a metadata error, after a MetadataRequest round trip. A subscribed consumer that sees new partitions rebalances its group | Modelled with the real default: producers and consumers use their cached partition counts until the next refresh, which is applied instantly at the next send / `poll()` once the age has passed (or after `UNKNOWN_TOPIC_OR_PARTITION`). The group leader's refresh triggers a rebalance that assigns the new partitions (only the leader watches metadata, as in the classic client); they start from `auto.offset.reset` | Shows the real "new partitions get no traffic for up to 5 minutes" and "`latest` skips records on new partitions" effects |
| New partition placement | `CreatePartitions` places new replicas with the controller's replica placer | Same placer as at creation, with a fresh random offset for the request and the topic's replication factor (M4-T2) | — |
| Topic IDs | Every topic gets a random 16-byte UUID topic ID when it is created (KIP-516); a deleted and re-created topic with the same name gets a new one | Topic IDs are sequence numbers (1, 2, 3, …) in creation order; a re-created topic still gets a new one | Deterministic and readable; only identity matters (snapshot diffs use it to spot a re-created topic) |
