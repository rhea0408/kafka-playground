# M4 decisions log

M4 starts with T0: the fixes from the M3 review (findings F-1 to F-9). As in M3, the rule is to **behave like real Kafka 4.x as closely as practical** and to write each decision down here, with the alternatives and the reason.

## Review these first

| # | Decision | Why it matters |
|---|---|---|
| [D1](#t0--m3-review-fixes) | **The onJoinPrepare auto-commit is sent once per rebalance.** Once it is answered, or after `rebalance.timeout.ms`, JoinGroup goes out without another commit. | Fixes F-1: under load, cooperative members never rejoined and were removed. |
| [D2](#t0--m3-review-fixes) | **The JoinGroup answer sets the generation; a successful SyncGroup makes the member stable at once.** `poll()` still applies the assignment. | Fixes F-2: busy cooperative members heartbeated with the old generation and lost their partitions. |
| [D3](#t0--m3-review-fixes) | **The commit invariant no longer requires the committer to own the partition in the current generation.** A member may commit a partition it still holds from the previous generation, and only one member commits a partition per generation. | This is an invariant change. The old one checked a rule Kafka doesn't have. |
| [D4](#t0--m3-review-fixes) | **A JoinGroup or SyncGroup that fails without a reset leaves the member PREPARING or COMPLETING**, with its member id, generation and partitions. Its commits fail on the client, and the retry skips onJoinPrepare (`needsJoinPrepare`). | Fixes the review of #42: a member fell back to STABLE in a generation that never completed, and the coordinator accepted its commits for it. This differs from the review's "UNJOINED", per the 4.0/4.1 source. |
| [L1](#liveness-bounds-found-by-the-f-3-property) | **A cooperative member with auto-commit needs two batches within the rebalance timeout**, plus one heartbeat interval. | This is real Kafka behaviour, not a bug. The liveness property (F-3, PR 2) uses this bound. |

## T0 – M3 review fixes

| # | Decision | Alternatives | Why |
|---|---|---|---|
| D1 | `ClientGroupState.prepareCommitDone` is set when the onJoinPrepare commit is answered (success or error) or when its wait times out. The next `joinGroup()` skips the commit and sends JoinGroup. The flag is cleared when JoinGroup is sent, on `resetGeneration`, and on close (`resetClientGroup`). The wait is limited by a sim-clock task, `ConsumerJoinPrepareTimeout`, after `max.poll.interval.ms` (the rebalance timeout). When it fires, the member joins and ignores the late answer. | Commit again at every `poll()` (the M3 behaviour, a livelock). Drop the "already committed" skip first (F-8): that would make eager members livelock too. | `ConsumerCoordinator#onJoinPrepare` sends the commit only while `autoCommitOffsetRequestFuture` is null, and keeps the future until it is done. `joinPrepareTimer` (rebalance timeout) ends the wait: "Asynchronous auto-commit of offsets failed: joinPrepare timeout. Will continue to join group". Checked against the trunk source (2026-11-04): the field comment reads "it'll set to rebalance timeout so that the member can join the group successfully even though offset commit failed". No ticket is named in the code. KAFKA-13310 ("KafkaConsumer cannot jump out of the poll method … blocked in … maybeAutoCommitOffsetsSync", fixed in 3.2.0, PR #11340) is the report about the old blocking commit. Its Jira text doesn't describe the fix, so the link to `joinPrepareTimer` is likely but not confirmed. |
| D2 | `onJoinResponse` sets `memberId` and `generation` from the answer. `onSyncResponse` sets `state = 'stable'` and `synced = true`, and stores the assignment, which `poll()` applies in `onJoinComplete` as before. A failed JoinGroup or SyncGroup without a reset is handled by D4. | Keep the generation update in `onJoinComplete` (the M3 bug). | `AbstractCoordinator.JoinGroupResponseHandler` stores the new `Generation`, and `SyncGroupResponseHandler` sets `state = MemberState.STABLE`, both on the network thread. So heartbeats in CompletingRebalance carry the new generation, and commits after SyncGroup succeed before the next `poll()`. |
| D3 | The invariant "an accepted commit comes from a member … that owns the partition" now also accepts a member that owned the partition in the **previous** completed generation and has not yet emitted `PartitionsRevoked` (or `PartitionsLost`) for it, so it is tied to the event log. New check: within one generation, only one member commits a given partition. | Drop the ownership check (too weak). Keep it (it rejects real Kafka behaviour once D2 is in). | `ClassicGroup#validateOffsetCommit` checks only the member id, the generation and the group state, never ownership. After D2, a cooperative member is STABLE in generation N+1 but revokes the partitions it gives up only at its next `poll()`. Until then it may commit them with N+1, and Kafka accepts that. No one else can own those partitions in N+1, because they move only in the follow-up rebalance (KIP-429). The new check therefore catches what the old one was protecting against. The F-2 regression test pins one such commit (c1, P2, generation 2). |
| D4 | A JoinGroup or SyncGroup that fails without a reset (`REBALANCE_IN_PROGRESS`, `COORDINATOR_NOT_AVAILABLE`) sets `joinRetry` and requests a rejoin. The state stays `preparing` or `completing`, and the member id, generation and owned partitions are kept. So: commits fail on the client with `REBALANCE_IN_PROGRESS` (not STABLE); heartbeats continue while `completing` and stay off while `preparing`; and the next `poll()` sends JoinGroup again. `needsJoinPrepare` (new, Kafka's flag) is cleared when onJoinPrepare finishes and set again only by `onJoinComplete` or a reset, so the retry skips the pre-rebalance commit and the revocation. `resetGeneration` now also clears `prepareCommitId`, the "answered" flag and the join-prepare timer. The `synced` field and the fallback to `stable` are gone. | Fall back to STABLE (the bug: a member stable in generation N, which never completes, had commits for N accepted while the coordinator prepared N+1). Set UNJOINED and stop heartbeats (the review's suggestion; the 4.x source does not do this). | 4.0 and 4.1 `AbstractCoordinator`: the `initiateJoinGroup` failure listener only records a metric (`failedRebalanceSensor`). The JoinGroup and SyncGroup handlers for `REBALANCE_IN_PROGRESS` only log and `future.raise(error)`. `joinGroupIfNeeded` calls `requestRejoin` and loops, and `initiateJoinGroup` sets `PREPARING_REBALANCE` when it resends. `HeartbeatThread` disables itself on `hasNotJoinedGroup()` = UNJOINED or PREPARING_REBALANCE, so COMPLETING keeps heartbeating. `sendOffsetCommitRequest` fails with `RebalanceInProgressException` when `generationIfStable()` is null and a rebalance is in progress. `needsJoinPrepare` is set true only at the field's initialisation, after `onJoinComplete`, in `resetStateAndRejoin`, and when onJoinPrepare must wait. Regression test: c4 joins 2 ms before a cooperative rebalance completes. On the old code, c1 and c2 commit for generation 2, which never completes. |

## Liveness bounds found by the F-3 property

The liveness property (review F-3, lands in PR 2) was run locally against PR 1, 2000 cases. It found no new livelock. It did find two cases where the bound in the review ("batch time under `max.poll.interval.ms`") is too loose for real Kafka. Both traces match the client's behaviour, so they become the property's precondition, not engine changes.

| # | Finding |
|---|---|
| L1 | **Cooperative + auto-commit needs two batches.** At the first `poll()` after it learns of the rebalance, the member sends the onJoinPrepare commit, and that same `poll()` returns the next batch (K12). JoinGroup goes out only at the poll after that batch. Counterexample: 369 records × 59 ms = 21.8 s per batch, rebalance timeout 30.5 s. c1 polled at 69.4 s (sent the commit, got a batch) and would have joined at about 91.2 s. The join phase ended at 79.6 s, so it was removed (`rebalance-timeout`). Eager members return nothing while the commit is in flight, so one batch is enough for them. |
| L2 | **Add one heartbeat interval.** A member learns of a rebalance only from a Heartbeat answer (`REBALANCE_IN_PROGRESS`), so it may start a new batch just before it hears. Counterexample: range, 3.9 s batches, `heartbeat.interval.ms` 2.5 s, rebalance timeout 5.3 s. c3 was removed at 26.37 s and would have joined at 26.42 s. |

The precondition is: `batches × batch time + heartbeat.interval.ms + 1 s < max.poll.interval.ms`, where `batches` is 2 for a cooperative member with auto-commit and 1 otherwise. L1 is a good Break-it candidate for a later level: "cooperative isn't free when batches are long."
