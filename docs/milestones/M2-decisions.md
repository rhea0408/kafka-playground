# M2 decisions log

Rhea asked for M2 to be built unattended. Where a decision was needed, the rule was: **behave like real Kafka 4.x as closely as practical**, and write the decision down here. Each entry gives the decision, the alternatives and the reason. Review these first.

## Process

| # | Decision | Alternatives | Why |
|---|---|---|---|
| P1 | Each task is its own `m2-t<k>` branch, **stacked** on the previous task's branch (`m2-t0` from `develop`, `m2-t1` from `m2-t0`, …). Each has a PR based on the previous branch, and CI must be green. **Nothing is merged**: merging without review was blocked, and the M1 no-review rule was only for M1. | Merge each PR after green CI (as in M1) | Review stays with Rhea. To merge: review the PRs in order, merging `m2-t0` into `develop` first. When a merged branch is deleted, GitHub moves the next PR's base to `develop`. If it doesn't, change the base with `gh api -X PATCH …/pulls/N -f base=develop`, then close and reopen the PR. |
| P2 | The milestone doc already approves the M2 dependencies. Any other dependency is listed under its task below with the reason. | Stop and ask | Rhea is away. These are small companion packages (test DOM, React types). |

## T2 · Engine additions for the UI

| # | Decision | Alternatives | Why |
|---|---|---|---|
| T2-1 | Partition decrease reason uses the **KRaft controller's** `InvalidPartitionsException` text: "The topic orders currently has 3 partition(s); 2 would not be an increase." plus one plain sentence ("Kafka can add partitions to a topic but never remove them."). | The ZooKeeper-era text "Topic currently has N partitions, which is higher than the requested M." | Kafka 4.x is KRaft-only; the text was checked in `ReplicationControlManager#createPartitions` on trunk. |
| T2-2 | **New partitions reach clients via `metadata.max.age.ms`** (new field on producer and consumer, real default 300000 = 5 min). Each client caches partition counts per topic; the cache is refreshed (applied instantly) at the next send / `poll()` once the age has passed, or after an `UNKNOWN_TOPIC_OR_PARTITION` error. A topic seen for the first time is fetched at once (KIP-526). The producer's sticky state for a topic is reset when a refresh changes its count. | Clients see new partitions at once (simpler, but teaches the wrong thing) | Closest to real Kafka, and it shows two real surprises: new partitions get no traffic for up to 5 min, and a consumer with `auto.offset.reset=latest` that picks them up later than the producer skips records (tested). The properties panel (T10) should show this field and mention it next to the "adding partitions" warning. The refresh round trip is not modelled (simplifications: "Client metadata refresh"). |
| T2-3 | A subscribed consumer adds new partitions to its assignment at its refresh **without a rebalance**; existing positions are kept; new partitions start via committed offset / `auto.offset.reset`. | Model a classic rebalance | Groups and rebalancing are M3. |
| T2-4 | New partitions continue the topic's stripe over the current brokers sorted by id from partition 0's leader (no RNG). | Fresh random start like topic creation | Deterministic and simple; with one broker (M2) they all land on it. Recorded in simplifications. |
| T2-5 | **Rate change does not start a new producer life.** It starts a new *send schedule* (`schedule` counter on the producer; ticks of older schedules are ignored). The producer's incarnation (its life, used in trace ids and to match produce responses) stays. | Bump the incarnation as the milestone text says ("new incarnation") | Bumping the incarnation would make the engine drop the responses of requests already in flight (they are matched by incarnation), so stats would stop counting acks. Trace ids stay unique because the record counter keeps increasing within a life. |
| T2-6 | **Trace ids** are `<producerId>@<incarnation>#<n>` (e.g. `p1@3#7`). `n` is the producer's record count, kept across rate changes; the incarnation is global and changes when a producer is removed and re-added. A fast-check invariant checks uniqueness over random runs that re-add producers and change rates. | Global record counter | Readable, and keeps the per-producer count visible. |
| T2-7 | A patch that changes nothing is **accepted (`ok: true`) with no event and no command-log entry**. A patch with unknown fields is rejected ("A producer has no config field …"). | Emit `ConfigUpdated` anyway; log it | Saving an unchanged properties form should not create noise in the event list or the log. Kafka itself rejects a same-count `CreatePartitions`, but a full-form save is not that request. Unknown fields would otherwise be silently stripped by Zod. |
| T2-8 | **Broker config changes are rejected.** The only broker field is `rack` (`broker.rack`), a static config read at broker start. | Accept and store it | Faithful; restarting brokers arrives in M4. |
| T2-9 | Topic: `replicationFactor` change rejected (reassignment, M4); `minInsyncReplicas` accepted (a dynamic topic config). | Reject everything but partitions | Matches what `kafka-configs` / `kafka-topics --alter` allow. |
| T2-10 | Consumer: `groupId` and `autoOffsetReset` changes rejected (M3). All other consumer fields apply from the next `poll()`; a fetch already parked at the broker keeps the min/max values it was sent with. Changing the config does not wake a consumer blocked in `poll()`. | Wake it immediately | The blocked poll ends by itself within `fetch.max.wait.ms`; no extra scheduling. |
| T2-11 | **Long-poll fetch** modelled on the *classic* `KafkaConsumer` (the 4.x default `group.protocol`): fetches are sent only from inside `poll()`, one request per leader with no request in flight to it, for partitions with nothing buffered; the broker parks a request in a purgatory until `fetch.min.bytes` (summed over the request's partitions) are below the HW or `fetch.max.wait.ms` passes; the HW moving wakes parked requests; responses fill a fetch buffer; `poll()` returns buffered records first (at most `max.poll.records`, leftovers stay buffered) and sends the next fetch **before** returning records (pipelining, i.e. prefetching, which turned out cheap). A blocked `poll()` also wakes at the auto-commit deadline (`timeToNextPoll`). | Background fetcher (KIP-848 consumer); no prefetch | Classic is the default in 4.x; the source comments cited in `consume.ts` were checked on trunk. |
| T2-12 | `fetch.max.bytes` and `max.partition.fetch.bytes` are **not modelled** (documented): a response carries every available record. Offset lookups (OffsetFetch / ListOffsets) are instant. Fetch sessions (KIP-227) not modelled; partition order in requests rotates by one per request. | Model the byte caps | They only matter for large backlogs; adds two schema fields for little teaching value. |
| T2-13 | `fetchMinBytes` and `fetchMaxWaitMs` allow 0 (as Kafka does); `fetchMaxWaitMs: 0` answers at once. `metadataMaxAgeMs` allows 0 (refresh on every send / poll). | Minimum 1 | Matches the Kafka config validators (`atLeast(0)`). |
| T2-14 | Records carry `sizeBytes` (the producer's `messageSizeBytes`, also for `ProduceManual` records) so `fetch.min.bytes` can count bytes. Visible in snapshots. | Count records instead of bytes | `fetch.min.bytes` is about bytes. |
| T2-15 | Fetch errors: a deleted topic completes parked fetches at once with `UNKNOWN_TOPIC_OR_PARTITION` (the consumer then requests a metadata refresh); a fetch offset outside [log start, HW] gets `OFFSET_OUT_OF_RANGE` and the consumer resets with `auto.offset.reset`. Responses for partitions no longer assigned, or whose position moved, are discarded (`FetchCollector`). | Let them time out | Matches `ReplicaManager` / `FetchCollector`. |
| T2-16 | A consumer blocked in `poll()` is woken when it is connected to a topic (like `subscribe()` to a new topic); Disconnect is handled at the next `poll()`. | No wake (it would wait up to the auto-commit interval or forever with auto-commit off) | Avoids a consumer that never notices a new connection. |
| T2-17 | No new events for fetch requests/responses. | `FetchSent` / `FetchCompleted` events | Not needed by the UI yet; avoids growing the event stream. Easy to add for a later "fetch" animation. |
| T2-18 | Docs: architecture §4.5 gains `ConfigUpdated`; §4.4 already listed `UpdateConfig`. The rest of §4.4/§4.5 (Q2 `LagChanged`, Pause/SetSpeed not being commands) is left to T13. | — | Task scope. |
| T2-19 | Demo script: at half time it raises p1's rate to 4 msg/s and grows `orders` to 4 partitions, and explains why the new partition stays empty (metadata age). | — | Shows `ConfigUpdated` and the metadata delay headlessly. |
