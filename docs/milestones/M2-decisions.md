# M2 decisions log

Rhea asked for M2 to be built unattended. Where a decision was needed, the rule was: **behave like real Kafka 4.x as closely as practical**, and write the decision down here. Each entry gives the decision, the alternatives and the reason. Review these first.

## Process

| # | Decision | Alternatives | Why |
|---|---|---|---|
| P1 | Each task is its own `m2-t<k>` branch, **stacked** on the previous task's branch (`m2-t0` from `develop`, `m2-t1` from `m2-t0`, …). Each has a PR based on the previous branch, and CI must be green. **Nothing is merged**: merging without review was blocked, and the M1 no-review rule was only for M1. | Merge each PR after green CI (as in M1) | Review stays with Rhea. To merge: review the PRs in order, merging `m2-t0` into `develop` first. When a merged branch is deleted, GitHub moves the next PR's base to `develop`. If it doesn't, change the base with `gh api -X PATCH …/pulls/N -f base=develop`, then close and reopen the PR. |
| P2 | The milestone doc already approves the M2 dependencies. Any other dependency is listed under its task below with the reason. | Stop and ask | Rhea is away. These are small companion packages (test DOM, React types). |

## T2 · Engine additions for the UI

| # | Decision | Alternatives | Why |
|---|---|---|---|
| T2-1 | Partition decrease reason uses the **KRaft controller's** `InvalidPartitionsException` text: "The topic orders currently has 3 partition(s); 2 would not be an increase." plus one plain sentence ("Kafka can add partitions to a topic but never remove them."). | The ZooKeeper-era text "Topic currently has N partitions, which is higher than the requested M." | Kafka 4.x is KRaft-only; the text was checked in `ReplicationControlManager#createPartitions` on trunk. |
| T2-2 | **New partitions reach clients via `metadata.max.age.ms`** (new field on producer and consumer, real default 300000 = 5 min). Each client caches partition counts per topic; the cache is refreshed (applied instantly) at the next send / `poll()` once the age has passed, or after an `UNKNOWN_TOPIC_OR_PARTITION` error. A topic seen for the first time is fetched at once (KIP-526). The producer's sticky state for a topic is reset when a refresh changes its count. | Clients see new partitions at once (simpler, but teaches the wrong thing) | Closest to real Kafka, and it shows two real surprises: new partitions get no traffic for up to 5 min, and a consumer with `auto.offset.reset=latest` that picks them up later than the producer skips records (tested). The properties panel (T10) should show this field and mention it next to the "adding partitions" warning. The refresh round trip is not modelled (simplifications: "Client metadata refresh"). |
| T2-3 | A subscribed consumer adds new partitions to its assignment at its refresh **without a rebalance**; existing positions are kept; new partitions start via committed offset / `auto.offset.reset`. | Model a classic rebalance | Groups and rebalancing are M3. |
| T2-4 | New partitions continue the topic's stripe over the current brokers sorted by id from partition 0's leader (no RNG). | Fresh random start like topic creation | Deterministic and simple; with one broker (M2) they all land on it. Recorded in simplifications. |
| T2-5 | **Rate change does not start a new producer life.** It starts a new *send schedule* (`schedule` counter on the producer; ticks of older schedules are ignored). The producer's incarnation (its life, used in trace ids and to match produce responses) stays. | Bump the incarnation as the milestone text says ("new incarnation") | Bumping the incarnation would make the engine drop the responses of requests already in flight (they are matched by incarnation), so stats would stop counting acks. Trace ids stay unique because the record counter keeps increasing within a life. |
| T2-6 | **Trace ids** are `<producerId>@<incarnation>#<n>` (e.g. `p1@3#7`). `n` is the producer's record count, kept across rate changes; the incarnation is global and changes when a producer is removed and re-added. A fast-check invariant checks uniqueness over random runs that re-add producers and change rates. | Global record counter | Readable, and keeps the per-producer count visible. |
| T2-7 | A patch that changes nothing is **accepted (`ok: true`) with no event and no command-log entry**. A patch with unknown fields is rejected ("A producer has no config field …"). | Emit `ConfigUpdated` anyway; log it | Saving an unchanged properties form should not create noise in the event list or the log. Kafka itself rejects a same-count `CreatePartitions`, but a full-form save is not that request. Unknown fields would otherwise be silently stripped by Zod. |
| T2-8 | **Broker config changes are rejected.** The only broker field is `rack` (`broker.rack`), a static config read at broker start. | Accept and store it | Faithful; restarting brokers arrives in M4. |
| T2-9 | Topic: `replicationFactor` change rejected (reassignment, M4); `minInsyncReplicas` accepted (a dynamic topic config). | Reject everything but partitions | Matches what `kafka-configs` / `kafka-topics --alter` allow. |
| T2-10 | Consumer: `groupId` and `autoOffsetReset` changes rejected (M3). All other consumer fields apply from the next `poll()`; a fetch already parked at the broker keeps the min/max values it was sent with. Changing the config does not wake a consumer blocked in `poll()`. | Wake it immediately | The blocked poll ends by itself within `fetch.max.wait.ms`; no extra scheduling. |
| T2-11 | **Long-poll fetch** modelled on the *classic* `KafkaConsumer` (the 4.x default `group.protocol`): fetches are sent only from inside `poll()`, one request per leader with no request in flight to it, for partitions with nothing buffered; the broker parks a request in a purgatory until `fetch.min.bytes` (summed over the request's partitions) are below the HW or `fetch.max.wait.ms` passes; the HW moving wakes parked requests; responses fill a fetch buffer; `poll()` returns buffered records first (at most `max.poll.records`, leftovers stay buffered) and sends the next fetch **before** returning records (pipelining, i.e. prefetching, which turned out cheap). A blocked `poll()` also wakes at the auto-commit deadline (`timeToNextPoll`). | Background fetcher (KIP-848 consumer); no prefetch | Classic is the default in 4.x; the source comments cited in `consume.ts` were checked on trunk. |
| T2-12 | `fetch.max.bytes` and `max.partition.fetch.bytes` are **not modelled** (documented): a response carries every available record. Offset lookups (OffsetFetch / ListOffsets) are instant. Fetch sessions (KIP-227) not modelled; partition order in requests rotates by one per request. | Model the byte caps | They only matter for large backlogs; adds two schema fields for little teaching value. |
| T2-13 | `fetchMinBytes` and `fetchMaxWaitMs` allow 0 (as Kafka does); `fetchMaxWaitMs: 0` answers at once. `metadataMaxAgeMs` allows 0 (refresh on every send / poll). | Minimum 1 | Matches the Kafka config validators (`atLeast(0)`). |
| T2-14 | Records carry `sizeBytes` (the producer's `messageSizeBytes`, also for `ProduceManual` records) so `fetch.min.bytes` can count bytes. Visible in snapshots. | Count records instead of bytes | `fetch.min.bytes` is about bytes. |
| T2-15 | Fetch errors: a deleted topic completes parked fetches at once with `UNKNOWN_TOPIC_OR_PARTITION` (the consumer then requests a metadata refresh); a fetch offset outside [log start, HW] gets `OFFSET_OUT_OF_RANGE` and the consumer resets with `auto.offset.reset`. Responses for partitions no longer assigned, or whose position moved, are discarded (`FetchCollector`). | Let them time out | Matches `ReplicaManager` / `FetchCollector`. |
| T2-16 | A consumer blocked in `poll()` is woken when it is connected to a topic (like `subscribe()` to a new topic); Disconnect is handled at the next `poll()`. | No wake (it would wait up to the auto-commit interval or forever with auto-commit off) | Avoids a consumer that never notices a new connection. |
| T2-17 | No new events for fetch requests/responses. | `FetchSent` / `FetchCompleted` events | Not needed by the UI yet; avoids growing the event stream. Easy to add for a later "fetch" animation. |
| T2-18 | Docs: architecture §4.5 gains `ConfigUpdated`; §4.4 already listed `UpdateConfig`. The rest of §4.4/§4.5 (Q2 `LagChanged`, Pause/SetSpeed not being commands) is left to T13. | — | Task scope. |
| T2-19 | Demo script: at half time it raises p1's rate to 4 msg/s and grows `orders` to 4 partitions, and explains why the new partition stays empty (metadata age). | — | Shows `ConfigUpdated` and the metadata delay headlessly. |

## T3 · Snapshot diff

| # | Decision | Alternatives | Why |
|---|---|---|---|
| T3-1 | **Targeted copy in `getSnapshot()`**: component configs and connections are deep-copied with a small `copyPlain`; stats objects are spread; offsets are numbers; **log records are frozen when appended** (`Object.freeze` in `appendRecord`) and shared with the engine, in a fresh array per snapshot. | Copy every record; deep-freeze the whole snapshot | Records are the bulk of a snapshot and never change once appended, so sharing them frozen is safe (a write throws `TypeError`) and costs nothing. Configs are few but are replaced, not mutated, by the engine; copying them keeps the "UI cannot mutate engine state" guarantee without auditing every config holder. Freezing whole snapshots would cost time every frame for no gain over `readonly` types. |
| T3-2 | **Topic ID (KIP-516) added**: `TopicState.topicId` / `TopicSnapshot.topicId`, a sequence number from `counters.topic`, new on every topic creation. A diff sends a topic whole when its ID changed. | Detect re-creation from offsets only | Kafka itself tells a re-created topic from the old one by its topic ID, so this is the faithful signal; it is also useful to the UI later. Ours is a number, not a random UUID (simplifications: "Topic IDs"). Not shown in events; no RNG use, so the event log is unchanged. |
| T3-3 | **Second guard on append-only**: within the same topic ID, the records `prev` and `next` share in their windows are compared field by field; any mismatch (offsets going backwards, windows that do not line up) sends the whole partition. Partitions that shrink or whose indices are not 0..n-1 send the whole topic. | Trust append-only | Makes `applyDiff ∘ diffSnapshot` correct for *any* pair of snapshots, even from different engines (e.g. after `reset()` in T4) or backwards in time. The property test checks every pair of snapshots in a run, both directions. |
| T3-4 | Diff shape: `SnapshotDiff` has one optional key per snapshot field (`t`, `brokers`, `topics`, `producers`, `consumers`, `groups`, `connections`); unchanged fields are left out, so **no change ⇒ `{}`** (`isEmptyDiff`). Keyed lists use `{ changed?, removed?, order? }`; `order` is only sent when the id order is not "prev minus removed, then new ids" (e.g. a component removed and re-added with the same id moves to the end). Producers, consumers, brokers and groups are sent whole when changed; topics as `{ config?, partitions? }` with partition entries `{ index, leader, logStartOffset, logEndOffset, highWatermark, drop, append }` or `{ index, full }`. Connections are sent whole when anything changed. | Diff consumer partition lists too; JSON-patch style ops | Simple, structured-clone friendly (plain objects/arrays only) and compact enough: the per-frame payload is dominated by the appended records. Consumer partition lists could be diffed later if profiling shows the need. A mapped type ties `SnapshotDiff` to `EngineSnapshot`'s keys, so a new snapshot field fails to compile until it gets a diff. |
| T3-5 | `applyDiff` returns `prev` itself for an empty diff, shares every unchanged entry/array with `prev`, and throws `"Snapshot diff does not fit …"` when a diff refers to an entry `prev` does not have. | Silently ignore | A mismatched frame is a host bug (T4); failing loudly makes it visible. The host should send a full snapshot after `init`/`reset`. |
| T3-6 | The benchmark lives in `packages/engine/scripts/snapshot-diff.perf.test.ts` (runs with `pnpm test`) because it reads `performance.now()`, which ESLint bans in engine `src/`. Setup: 10 topics × 100 partitions, 10 producers at 400 msg/s with 400 random keys, 2 consumers, 6 s warm-up (~17,000 records in the 20-record windows). It checks the **median of 15 frames < 33 ms** (one whole frame) for snapshot + diff. | Put it in `src/` with eslint-disable; Vitest `bench` | Keeps the determinism lint rule absolute in `src/`; a normal test runs in CI. The generous bound makes it robust on slow CI while still catching an order-of-magnitude regression. |
| T3-7 | **Measured (WSL2 laptop, Node 22):** median snapshot 0.49–0.59 ms, diff 0.44–0.52 ms, total **0.94–1.11 ms** per frame (3 runs). For comparison the old JSON deep copy of the same snapshot alone took a median of **~19 ms**. | — | Recorded as the task asks. |


## T4 · Worker host and Comlink API

| # | Decision | Alternatives | Why |
|---|---|---|---|
| T4-1 | `SimHost` (`apps/web/src/sim/sim-host.ts`) is a plain class with an injected wall clock (`now()`) and tick scheduler (`scheduleTick(cb) → cancel`). The worker gives it `performance.now` and `setTimeout(tick, 16)` (~60 Hz ticks). `sim.worker.ts` only adds Comlink and proxy bookkeeping; `sim-client.ts` creates the module worker and `Comlink.wrap`s it. The API type (`SimApi`) and frame types live in `protocol.ts`, which has no DOM or worker globals. | `requestAnimationFrame` in the worker | rAF in dedicated workers is not available in every browser; `setTimeout` is. Keeping the API type out of the worker file lets the main thread import it without type-checking the worker under the DOM lib. |
| T4-2 | Frames: `{ kind: 'full', snapshot, history }` after `init` / `reset` and as a new subscriber's first frame; otherwise `{ kind: 'diff', diff }`. Every frame also has `frame` (host-wide counter), `t`, `playing`, `speed` and `events` (all events since the previous frame). `applyFrame(prev, frame)` in `protocol.ts` rebuilds the snapshot. | Status via separate calls | The store (T5) can follow play state and speed from frames alone. |
| T4-3 | **Frames are lossless**: every event reaches every subscriber exactly once, in order, however many there are. The ring buffer (`EVENT_HISTORY_SIZE` = **10,000** events, NFR-2.9 gives no number) is only for history: `eventHistory()` and the `history` field of a late subscriber's full frame (events already delivered; the event list may show them but must not animate them). | Drop events from frames when the UI falls behind | The overlay, event list and later the level runtime must not miss events. Pending events are bounded by one tick of work (T4-5). If the main thread itself can't keep up with the frames, flow mode (v0.2) is the answer, not silent drops. 10,000 events is ~20 minutes at 2 msg/s and a few seconds at the 1,000 msg/s per-producer cap. |
| T4-4 | **No formatted text in frames.** The main thread calls `formatEvent` itself (pure, from `@kp/engine`). | Send a `lines[]` next to `events` | Halves the payload; the virtualised event list (T11) only formats visible rows. |
| T4-5 | **Tick cap `MAX_TICK_DELTA_MS` = 250 ms wall** per tick. Fractional sim ms are carried to the next tick (`carry`); the carry resets on `init` / `reset`. | No cap; 100 ms cap | Background tabs throttle worker timers to ≥ 1 s; without a cap the next tick would jump minutes. 250 ms is the usual game-loop limit: long enough to absorb a GC pause without slowing down, short enough that a hidden tab just runs slowly. Also prevents a slow tick from making the next one longer and longer. |
| T4-6 | **Frame rate**: the run loop sends a frame only if ≥ `FRAME_INTERVAL_MS` = 33 ms (wall) passed since the last one and something changed (non-empty diff or events). Explicit user actions (`play`, `pause`, `step`, `stepBy`, `setSpeed`, a `dispatch` while paused) send a frame at once, so the UI answers within NFR-2.6's 100 ms. While playing, `dispatch` does not flush; the next loop frame carries it. | Rate-limit user actions too | User actions are rare; waiting up to 33 ms for them adds latency for nothing. |
| T4-7 | `setSpeed` **rejects** values outside 0.25–10 (or non-finite) with `{ ok: false, reason }` and keeps the old speed. Changing speed while playing first runs the time up to now at the old speed. | Clamp | The UI only offers fixed presets, so an out-of-range value is a bug; rejecting shows it instead of hiding it. |
| T4-8 | `step()` and `stepBy(ms)` **pause** a running host first (running the wall time up to now). `stepBy` takes a whole number of ms ≥ 1, else it is rejected. `step()` returns `{ stepped, t }` (`stepped: false` when nothing is queued). | Step while playing | Debugger semantics; stepping a running loop is meaningless. |
| T4-9 | `reset()` and `init()` stop the loop (host is paused afterwards), keep the speed, clear the pending events, ring buffer and command log (fresh engine), and send a full frame with empty `history`. `init` with an invalid topology returns `{ ok: false, reason }` and keeps the previous engine. Calls other than `init`, `setSpeed`, `subscribe`, `status` and `eventHistory` throw before `init`. | Keep playing after reset | Reset means "back to the start"; the user presses Play again. |
| T4-10 | **`eventLogHash()` replays the command log** on a fresh engine to the same number of processed tasks (not just the same time, because `step()` can stop mid-instant) and hashes with the engine's FNV-1a. Incremental hashing of the live stream was measured at **+65 % engine CPU** at 2 × 1,000 msg/s (117 → 195 ms for 10 s of sim), so it is not "cheap". The engine's `hashEvents` (was test-only in `testing/run.ts`) moved to `packages/engine/src/events/hash.ts`, is exported, and gained `createEventHasher()` (incremental, same result, unit-tested), which the replay uses to avoid holding the whole log. | Hash live events; keep all events | Free in steady state. The replay runs the bundled engine in the worker, which is exactly what T12 compares with Node. The SimHost tests check that live frame events equal the replayed events, so the replay hash stands for the live run. |
| T4-11 | Multiple subscribers are supported; `subscribe` returns a numeric token, `unsubscribe(token)` releases the worker's Comlink proxy. A new subscriber triggers a flush to existing subscribers first, so its history contains only delivered events. Without subscribers the host still drains pending events (into the ring buffer only) and computes no snapshots. | Single subscriber | Comlink cannot return a plain function across the boundary; tokens keep it simple. |
| T4-12 | `apps/web/tsconfig.worker.json` (lib `ES2023` + `WebWorker`) checks `src/**/*.worker.ts` and what they import; `tsconfig.app.json` excludes them; `typecheck` runs all three. `apps/web` `test` script dropped `--passWithNoTests`. `comlink@^4.4.2` added (pre-approved). | — | Follow-ups from T0-6 and T0-9. |

## T5 · Stores and the command path

| # | Decision | Alternatives | Why |
|---|---|---|---|
| T5-1 | Three Zustand (`zustand@^5`, pre-approved) stores in `apps/web/src/stores/`: `useTopologyStore` (components in insertion order, connections, positions), `useSimStore` (snapshot, events, t, playing, speed, frame), `useUiStore` (selection `{ nodeIds, edgeIds }`, `rightTab` properties \| partition-log, `bottomTab` events \| lag \| timeline, toasts, reducedMotion). Updates are plain exported functions (`pushToast`, `applySimFrame`, …), not methods on the state. | Methods inside the stores; one combined store | Plain functions are callable outside React (actions, bootstrap, worker callbacks) and keep the state objects pure data. |
| T5-2 | The topology store holds **parsed** configs (schema defaults filled in), equal to the engine's snapshot configs. Tests check canvas and engine agree after every action. | Store the raw input | The properties panel (T10) needs every field's value; the defaults must match the engine's exactly. |
| T5-3 | **Id scheme:** kind prefix + number: `b1`, `t1`, `p1`, `c1`, next number = highest in use for that prefix + 1 (so ids never step backwards on one canvas). `addComponent` accepts an explicit `id` (e.g. a topic name the user typed). Same style as the engine's tests (`p1`, `c1`, `t1`, `b1`). | `producer-1`; smallest free number | Short ids fit node headers and match the engine tests and demo. Not reusing a lower number avoids "p1 came back" confusion in the event list; trace ids are unique across lives anyway (T2). |
| T5-4 | The Sandbox starts with **one broker `b1`** in the topology store, because M2 is single-broker and a topic needs a broker (RF ≤ brokers). T12 adds the default scene on top. | Empty canvas | Without a broker the first topic the user drops is refused. |
| T5-5 | **Removing a component sends one `RemoveComponent`**; the engine drops its connections in the same step (`commands/apply.ts`: atomic, one log entry, no `Disconnected` events). The UI drops the edges locally on `ok`, and removes the id from the selection. | UI sends `Disconnect`s first | One command is atomic (no half-removed state if a later command fails) and keeps the command log short. In real Kafka, deleting a topic also simply ends clients' use of it; there is no separate "unwire" step. |
| T5-6 | **Reset = `init({ seed, topology: <current canvas> })`**, not the host's `reset()`. The sim goes back to t = 0 with empty logs and a cleared command log, but the canvas the user built stays. | Host `reset()` (back to the topology given at `init`) | The host's initial topology is the empty Sandbox; resetting to it would wipe everything the user built. | F1 | **Committed offsets and topic re-creation** (`fix(engine)`, branch `m2-fix-invariant`). Deleting a topic now deletes every group's committed offsets for it (`deleteCommittedOffsets`, as `GroupCoordinator#onPartitionsDeleted` does).
