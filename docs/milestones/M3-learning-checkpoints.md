# M3 learning checkpoints

Short answers to the "Learning checkpoint" questions in `docs/milestones/M3-consumer-groups.md`. They are written for someone new to Kafka; each one links the Kafka behaviour to what the engine does.

## T2 · Assignors

**Q: With 2 topics of 3 partitions each and 4 consumers, what do range and round-robin each give? Why does range leave a consumer idle per topic?**

Say the members sort as c1 < c2 < c3 < c4 (Kafka sorts them by member id). **Range** works one topic at a time: it splits that topic's 3 partitions into contiguous ranges over the 4 members, so the first three get one each and c4 gets none, and then it does exactly the same for the second topic. The result is c1 = `t1-0, t2-0`, c2 = `t1-1, t2-1`, c3 = `t1-2, t2-2` and c4 = nothing: c4 is idle although the group has 6 partitions for 4 members. **Round-robin** first lists every partition of every topic (`t1-0 t1-1 t1-2 t2-0 t2-1 t2-2`) and deals them out like cards: c1 = `t1-0, t2-1`, c2 = `t1-1, t2-2`, c3 = `t1-2`, c4 = `t2-0`, so every member works. Range idles c4 because it never looks across topics: within one topic there are only 3 partitions to share, and the members that get the extra range are always the first ones in id order. That sounds like a flaw, but it is deliberate: range puts the same partition number of every topic on the same member (here `t1-1` and `t2-1` both go to c2), which is what you want when two topics are keyed the same way and the application joins them. Remember also that a partition is never split between members of one group, so a group never has more working members than it has partitions to give out (`assignors.test.ts` has this case).

## T3 · Group coordinator

**Q: Why does the *client* leader compute the assignment, and not the coordinator? (KIP-848 moves it to the broker.)**

In the classic protocol the broker deliberately knows nothing about what consumers do with partitions. JoinGroup carries each member's subscription as opaque bytes tagged with a protocol name ("range", "cooperative-sticky"), and the coordinator only checks that the members share a protocol and picks one by vote. One member, the leader, gets everyone's metadata in its JoinGroup response, runs the assignor *in its own process*, and sends the result back in SyncGroup; the coordinator just hands each member its slice. This keeps the broker generic. The same JoinGroup/SyncGroup machinery also serves Kafka Connect and Kafka Streams, which assign tasks rather than partitions. It also lets anyone plug in a custom assignor by putting a class on the client's classpath, without upgrading brokers. The price is what M3 shows: every change needs a group-wide barrier (everyone rejoins, then the leader decides), a slow member holds up the whole group, and the leader's possibly stale metadata decides what gets assigned. KIP-848 (`group.protocol=consumer`) moves the assignor to the broker, which knows the metadata and every member's state anyway. It then reconciles members one at a time through heartbeats, so there is no global barrier and no stop-the-world. In the engine, `group-coordinator.ts` is the classic broker side; the leader's assignor call arrives in T4.

## T4 · Consumer coordinator

**Q: What is the difference between a session timeout and a poll timeout, and which thread detects each?**

They watch two different things. The **session timeout** (`session.timeout.ms`, Kafka default 45 s, 10 s here) is about whether the *process* is alive. The consumer's background heartbeat thread sends a Heartbeat every `heartbeat.interval.ms` (3 s), and the **broker's group coordinator** removes a member it has not heard from for the session timeout. That catches crashes, frozen VMs and network splits: a killed consumer in the playground disappears about 10 s after its last heartbeat (`MemberRemoved`, reason `session-timeout`), then the group rebalances. The **poll timeout** (`max.poll.interval.ms`, Kafka default 5 min, 30 s here) is about whether the *application* is making progress. The heartbeat thread keeps beating even while your code is stuck processing a huge batch, so the coordinator would never notice. Instead the **client's own heartbeat thread** checks how long it has been since the application last called `poll()`; past the limit it sends LeaveGroup ("consumer poll timeout has expired") and forgets its member id. The application does not know yet: it keeps processing records it no longer owns (a *zombie*), and only at its next `poll()` does it find its partitions lost (`PartitionsLost`) and rejoin as a new member. In short, the session timeout is detected by the broker and needs no heartbeats arriving; the poll timeout is detected by the client and needs no `poll()` calls. Fix the first with healthier processes, the second with smaller batches (`max.poll.records`) or faster processing.
