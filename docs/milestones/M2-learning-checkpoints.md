# M2 learning checkpoints

Short answers to the "Learning checkpoint" questions in `docs/milestones/M2-web-shell.md`. They are written for someone new to Kafka; each one links the Kafka behaviour to what the engine does.

## T1 · Message timing

**Q: In real Kafka, what happens between `send()` returning and the record being readable by a consumer? Which of those steps does the engine model, and roughly how long does each one take?**

`send()` only puts the record into a per-partition batch in the producer's memory and returns at once. The batch waits until it is full or `linger.ms` has passed (5 ms by default since Kafka 4.0, KIP-1030), then goes over the network to the partition leader (well under 1 ms in one data centre). The leader appends it to its log in the page cache (microseconds), and the followers copy it; once every in-sync replica has it, the high watermark moves past it (about one or two network round trips). Only then can consumers read it, whatever `acks` the producer used: `acks` decides when the *producer* hears back, not when consumers can see the record. A consumer's fetch request is usually already waiting at the leader (long poll), so it is answered as soon as the high watermark moves, and `poll()` hands the record to the application; end to end that is a few milliseconds. The engine models the partitioner, a fixed 1 ms network hop each way, the leader append and the produce response, and from M2-T2 the long-poll fetch. It does not model linger or batching (each record is sent at once), disk time, or replication (one replica, so the high watermark moves on every append until M4). The dots on the canvas are deliberately much slower than all this; the partition log and counters show the real timing (ADR 0008).

## T2 · Engine additions for the UI

**Q: Why can't you reduce a topic's partition count? After adding partitions, which records for key `B` are where, and what does that do to per-key ordering for a consumer?**

A partition is an append-only log whose offsets are never reused, and producers, consumers and committed offsets all refer to records by (partition, offset). Removing a partition would mean deleting its records or moving them into other partitions with new offsets, which would break committed offsets and the order of every key in it, so Kafka simply refuses: "The topic orders currently has 3 partition(s); 2 would not be an increase." Adding partitions is allowed, but nothing moves: with 3 partitions key `B` hashes to partition 1 (`toPositive(murmur2("B")) % 3 = 1`), and with 4 partitions it hashes to partition 0 (`% 4 = 0`; with 5 it would be 1 again). So all old `B` records stay in `orders-1`, and once the producer refreshes its metadata (up to `metadata.max.age.ms`, 5 minutes by default) new `B` records go to `orders-0`. Kafka only guarantees order within one partition, so a consumer reading both partitions can now see a newer `B` from `orders-0` before an older `B` still waiting in `orders-1`: per-key ordering across the change is lost. (Watch out too: a consumer that discovers the new partition later than the producer, with `auto.offset.reset=latest`, skips the records written there in between.) That is why teams pick enough partitions up front for keyed topics, or create a new topic and migrate.

## T4 · Worker host and Comlink API

**Q: Why can the worker host read `performance.now()` when the engine can't? Why are speed and pause not in the command log?**

The engine must give the same event log for the same seed and commands, every time and on every machine (NFR-4.1); that is what makes replay, the determinism test, level verification and later the fidelity harness work. `performance.now()` returns a different value on every run, so if the engine read it, the outcome would depend on how fast the laptop was. The host sits outside that boundary: it only decides *how much* sim time to run right now (wall-clock delta × speed) and calls `runUntil(t)`, and the engine's result for "run until t" does not depend on how the time was chopped into ticks. Speed, pause and step work the same way: they change when we look at the simulation, not what happens in it, like pausing a video does not change the film. A command, by contrast, changes the simulated world (a new producer, a killed consumer), so it is logged with its exact position (`t` and `afterStep`) and a replay reproduces the run without knowing anything about speed or pauses. In real Kafka there is no "speed" at all: time is the broker's and clients' wall clock, which is exactly what our sim clock stands in for.
